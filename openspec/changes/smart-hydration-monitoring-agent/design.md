# Design

## Context

- 現況：Proposal 階段、無程式碼。Existing Resources 僅 Raspberry Pi 4；Load Cell、HX711、杯墊結構為 Planned。
- 動機與範圍見 `proposal.md`；行為契約見 `specs/`；五層架構與完整說明見根目錄 `DESIGN.md`。
- 約束：三人短期蒐集、小樣本；LLM 為外部服務；LINE Webhook 需公開 HTTPS，而 Raspberry Pi 通常在內網。

## Goals / Non-Goals

**Goals:**
- 打通「感測 → 事件辨識 → Agent 提醒 → LINE 回饋」完整鏈路，可 Demo。
- 讓「ML 預測」「確定性計算」「LLM 文字生成」三者責任分離、可稽核。
- 每個提醒決策可重現：輸入、護欄結果、輸出皆寫入紀錄。

**Non-Goals:**
- 不追求一般化的模型準確率宣稱；不做線上學習宣稱。
- 不提供醫療級補水建議，不推論水合狀態。

## Decisions

### D1 五層架構（IoT / Backend / ML / Agent / Application）
- 選擇：Raspberry Pi 收資料，FastAPI + SQLite 為中樞，ML 與 Agent 皆由 Backend 呼叫。
- 理由：單一資料來源，Dashboard、Agent、實驗皆讀同一份 SQLite，便於重現。
- 替代：Pi 上直接跑全部（耦合高、LINE Webhook 難處理）；雲端資料庫（成本與隱私）。

### D2 先切片段、再分類、最後才估量（兩階段）
- 選擇：Collector 先切出「拿起—放回」片段，Task A 分類，僅 Drinking 計入 `ΔW/ρ`。
- 理由：重量減少不等於飲水（倒水、移動、雜訊）；文獻亦採兩階段（Griffith 2019）。
- 替代：直接用 ΔW 門檻——保留為 Baseline，用於實驗 1 比較。
- 假設（未驗證）：水密度約 1 g/mL；使用者會把杯子放回杯墊。

### D3 決策責任切分：規則護欄 > ML 預測 > LLM 文字
- 選擇：護欄（冷卻、安靜時段、每日上限、目標已達、暫停）為確定性規則，LLM 不可覆寫；LLM 只生成通知文字，失敗或未通過詞彙檢查時用模板。
- 理由：規則透明可稽核；LLM「成功執行不等於決策適當」（Rezaee 2026）。
- 替代：LLM 全權決策（彈性高但難驗證、可能時機不佳）。

### D4 Task B 為次要且可降級
- 選擇：模型不可用或資料不足時，退回 Historical Average Rule，且不宣稱已建立可靠預測。
- 理由：三人短期資料量有限；評估採時間切分避免洩漏。

### D5 資料與隱私
- 選擇：只存必要欄位；傳給 LLM 的內容去識別化且只含必要欄位；不使用相機。

## Risks / Trade-offs

- [硬體到貨延遲] → 以標示為模擬資料的合成資料先驗證軟體流程，不將其用於任何準確率宣稱。
- [小樣本、順序與新奇效應] → 同一批使用者輪流使用三種策略並記錄順序，僅做描述性比較。
- [杯子未放回或直接對瓶口飲用而無法量測] → 在限制中明示；Dashboard 標示資料缺口。
- [LINE Webhook 需公開網址] → 以轉發方案處理（待確認），推播額度須查官方現行規定。
- [提醒造成干擾] → 冷卻、每日上限、安靜時段、使用者可暫停；以接受率與無效提醒比例監測。
- [LLM 輸出越界（醫療或脫水用語）] → 詞彙檢查，不通過則改用模板。
